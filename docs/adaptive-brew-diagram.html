📋 After-Shot Analysis — Two-Phase Data Population & why Shot Coach waits for phase ② (AdaptiveBrewCard.jsx → ShotCoach.jsx)
① At brew:end — immediate (live event push)
Firmware processPendingBrewEnd() fires evt:adaptive-brew:channeling-result
→ handler calls confirmShotInHistory() only when brewTimeSec ≥ 15 s, then polls /api/history/index.bin (0 / 1 / 3 / 8 s) and sets the channeling state.
Sub-15 s brews (flush / abort) populate nothing — the last real shot stays.

Carries: score · severity · eventCount · maxDrop · flowCV
extractionTime = brewTimeSec (wall-clock · marked provisional) · yield = ∅

Shows: CHANNELING ✓ · SHOT COACH … pending · GRIND ADVICE ✗
② After rating · Save&Learn / ↻ refresh (pull)
req:save-shot-rating → firmware learnFromShot(): persists channelingScore, db_.build(), fills lastBrewExtraction*_, runs PostShotGrindAdvisor.
Card then runs fetchPostShotData() in parallel:
  • req:grind-advice (actualGrind override)
  • req:channeling → now also returns
    extractionTime = durationMs/1000 (recorded .slog header)
    extractionYield = 18+(t−28)·0.3+(ratio−2)·2 (needs doseOut)

Shows: CHANNELING ✓ · SHOT COACH ✓ (first shown · final data) · GRIND ADVICE ✓
same path also fires on manual ↻ and on-connect catch-up
🧩 Section ▸ data source
CHANNELING — ChannelingDetector live score → lastChannelingResult_
identical in ① and ②; rating never recomputes it

SHOT COACH — matchScenarios(time, score, events, maxDrop, yield)
withheld in ① via the channeling.provisional flag — shows only with final data, like Grind Advice (see note)

GRIND ADVICE — PostShotGrindAdvisor → lastGrindAdvice_
pull-only: card has no listener for the grind-advice event, so it appears only after fetchPostShotData()
⚠ Mechanism — what is incomplete at brew:end (and would flip the Shot Coach verdict)
Two inputs to matchScenarios() are incomplete at brew:end. (1) yield = 0 blocks the yield-driven scenarios C (fast + low yield → too coarse), E (high yield + long → over-extracted) and F (clean shot) — only A / B / D / generic could match, and "What happened" would print ?%. (2) time is wall-clock brewTimeSec, not the recorded durationMs/1000, so it can sit in a different bucket (<18 · 25–35 · >50 s). Either would make the coach verdict change after rating, so the card hides it (via channeling.provisional) until fetchPostShotData() delivers final time + yield — then it appears once, alongside Grind Advice. Channeling score · events · maxDrop · flowCV are unaffected and show immediately in ①.
🧭 How to use it — correlate Grind Advice (post-shot) with the next Recommended Grind (don't chain them)
① After the shot — act & rate
Read Grind Advice — a Δ relative to the grind you actually used.
→ move the grinder that many steps → pull the next shot → rate it.
The rating feeds learnFromShot(), so the model absorbs this shot's outcome before the next recommendation.
Advice is the responsive, immediate single-shot correction.
② Before next shot — correlate the two deltas
Both deltas share the same base (your last grind):
• Grind Advice "↑/↓ N steps" — rule, last shot only
• Recommendation "vs last shot" badge — model, all history
Agree in direction → confident, go.
Disagree: <5 bean shots → trust Advice (model still sluggish); ≥5 → trust Recommendation (it already absorbed the last shot).
③ Don't double-count — cautions
Never add Advice onto the Recommendation. Once rated, the model already includes that shot — chaining applies the fix twice → oscillation / hunting.
Trend ×1.2 / ×1.4 (several recent shots agree) → move decisively; a lone un-trended nudge on a dialed-in bean is likely noise.
Channeling as the primary factor → fix puck prep (distribution / tamp) first, not grind.
